我的博客早就有了ActivityPub支持，当时还是手工编程时代，我照着已有的教程和[wildebeest](https://github.com/cloudflare/wildebeest)做的。在几天又痛又快乐的开发以后，我摘下了几颗低垂的果实：在联邦宇宙里搜索本文链接，就能找到文章的标题和摘要，点击作者头像就能找到这个博客对应的账号（Actor），关注它，就能订阅文章之后的更新。如此这般，我可以发文章，读者能收到推送，还可以评论，我们都有美好的未来。

吧？

让我们看看此前的实现：收件箱只处理了“关注”和“取消关注”这两种请求，如果有用户回复我的帖子，就简单在控制台记个Not Implemented，然后返回成功来骗人。这样一来，用户所在的实例会有这条回复，但其它实例看不见，而且我也只能找log看。

至于“订阅”，Fediverse是这样要求的：在文章有更新时，需要向所有关注者的Inbox投递特定文章。我的实现是，带Token调用一个接口，接口会把整个outbox重新发一遍。至于请求失败怎么办、执行到一半挂了怎么办——当然是凉拌了。事已至此，先吃饭吧。

支持ActivityPub真是太简单啦！json-ld极大丰富，能关注，复制文章链接也能搜到，如果再加上真实的评论机制，我的博客就进入了理想中的Fediverse社会。但我的生产力匹配不了更进一步的物质文化需求，于是博客的ActivityPub实现就一直停在了这个初级阶段。

这一等就是两年。这两年里，我溜出了时代银行的后门，在被LLM碾过之前找到了实习和正式岗，还[结了婚](/posts/Marriage)、逐渐成为了现充。在写其它Side Project时，我找到了一个很好用的命令行参数处理库[optique](https://github.com/dahlia/optique)，顺手看了眼[作者](https://github.com/dahlia)——怎么是they/them？

对的对的，非二元的，语言学的，自由软件开发者，交叉性女性主义者。这太合我胃口了，毫不犹豫地开始赞助，顺手给他的韩日台港中计算机常用词对照[网站](https://cjk-compsci-terms.netlify.app/)交了个[issue](https://github.com/dahlia/cjk-compsci-terms/issues/21)。

又过了半年，他搞出[Fedify](https://fedify.dev/)，彻底解决了TypeScript和Cloudflare Worker接入ActivityPub的问题。我博客的ActivityPub实现终于有救了。

## 首先，让我们看看它到底支持了什么

此前的实现其实很直白：WebFinger负责让别人找到账号，actor接口描述“我是谁”，每篇文章转成一个Note，再套上一层Create，放进outbox。关注者的actor地址和inbox地址存进Cloudflare D1，需要发文章时，把Create签名后POST过去。

这里的Note一直只包含文章标题、摘要和链接，并没有把整篇博客塞进联邦时间线。这次迁移也延续了这个做法。

发送请求时，我有一个继承自Request的AppRequest，负责计算Digest和生成HTTP签名。围绕这件事，仓库里还放着签名处理、解析器、校验器等一串文件。

有签名，有解析器，还有校验器，看起来收发双方都能得到周全的身份验证。然而顺着收件箱入口找过去，会发现它直接调用了 `request.json()`，然后根据body里的type分支处理，根本没有接上验签。也就是说，我向别人证明“我确实是我”时相当认真，别人来告诉我“我是谁”时，我却选择了全盘相信——很符合一个刚接触社会、尚且没有挨过毒打的博客的形象。

旧收件箱的核心逻辑如下，省略了类型转换：

```typescript
switch (body.type) {
  case 'Follow':
    return handleFollow(body, db, env);
  case 'Undo':
    return handleUnfollow(body, db);
  default:
    console.error(new Error(`Not Implemented: ${body.type}`));
    return new Response('Ok');
}
```

关注会写入数据库，再给对方发一个Accept；取消关注会删除记录。至于回复文章的Create、编辑回复的Update、删除回复的Delete，则一律打印报错，再返回“Ok”。这样一来，对方得到了成功响应，我得到了错误日志，唯独评论本身没有得到任何去处。一个把读者发言直接扔掉的收件箱，竟然还颇有礼貌，每扔一条都要答复一句“好的”。

## 把协议代码交给Fedify

第一步是把手工拼ActivityStreams对象、处理签名和发送活动的部分换掉。现在用的是Fedify，以及它的词汇库 `@fedify/vocab`。

例如，文章依然转换成Note，但现在创建的是一个 `new Note(...)`，账号则是 `new Person(...)`。具体URL对应什么对象、收到什么活动该做什么，通过dispatcher和listener注册。JSON-LD序列化、入站验签和出站签名投递交给Fedify，博客自己负责找文章、存关注者和处理回复。

原来那串签名相关文件于是可以删除了。之前[给waline瘦身](/posts/walineServerSlim/)时，我想方设法地移除依赖，这次却主动引入了一个框架，显得很不坚定。不过我对“自己实现”并没有什么忠诚可言，何况已经自己实现到连验签都没接上的程度。这次没有比较迁移前后的包体积，至少以后不用再维护这一串代码了。

不过，在把旧实现删掉以前，还得留下原来的账号身份。博客已经有关注者，文章对象也已经发给了别人，如果连actor地址、Note地址和签名密钥都一起换掉，我当然知道这是我的博客，远端服务器却没有义务和我心有灵犀。重构一次，就要让读者重新关注一次，也不知道是在维护博客还是在清退读者。

因此，这次保留了这些东西：

- actor仍然是 `https://blog.yunyi.beiyan.us/api/activitypub/actor`。
- 文章的Note和Create仍然使用原来的URL和slug。
- 继续使用原来的RSA密钥对，公钥ID仍然是 `#main-key`。
- D1里原有的follower表及关注者记录继续使用。
- WebFinger继续识别原来的账号，以及 `stblog.penclub.club` 这个站点别名。

Fedify内部用于匹配路径的identifier设成了 `activitypub`，公开用户名则还是 `BeiyanYunyi`。这样以后，代码里面可以换得面目全非，对外仍然是原来的账号，D1里的关注者也不需要挪窝。

浏览器访问文章时得到HTML，联邦客户端明确请求ActivityPub JSON时得到Note，这部分内容协商也继续保留。它在迁移前就已经能用，倒也不能为了显得这次改造很有成效，就把旧功能拿来重新报喜。

## 确实是你，然后呢

接上验签以后，至少可以知道消息确实是签名者发来的。然而甲完全可以签名发来一个Undo，要求撤销乙的关注——签名是真的，甲也确实是甲，但这和乙有什么关系？不能因为来人带了身份证，就允许其替别人办退订。

于是这里还需要检查活动之间的关系：Follow必须指向本博客，Undo所撤销的Follow也必须指向本博客，发起Undo的人则必须是原来发起Follow的人。关注确认的顺序也改了一下，先把Accept持久化入队，再保存关注者。否则这边已经把人记进关注列表，那边却迟迟收不到确认，双方就对彼此的关系产生了不同认知，颇不利于联邦团结。

接下来是给它留一点记性。对方没有及时收到响应，就可能重发同一条活动；而Worker下一次请求未必还在同一个实例里处理，如果把“这条消息已经处理过”的记录留在内存里，换个实例以后就又得重新认识一遍。显然，联邦关系不能只靠这点短暂的记忆维持。

我于是写了一个D1KvStore，用D1保存Fedify所需的缓存和成功处理过的入站活动记录。取值、写入、删除、遍历和过期时间处理都在这个适配器里，数据库新增一张 `fedify_kv` 表即可。现成的D1还能继续用，倒也不必为了名字里有个“KV”，就再去开一个Workers KV命名空间。

## 给评论找个去处

这样以后，账号身份保住了，签名也开始验证了，可以比较放心地接收读者回复——然后继续把它扔掉，因为还没写存储。看来还是得继续干。

现在收到指向本地文章Note的直接回复，会把远端对象ID、本地文章slug、作者、回复目标、HTML内容和时间存进 `ap_comment`。但并不是随便发一个带有inReplyTo的JSON就能入库：目标必须对应一篇确实存在的本地文章，Note的署名必须与活动发送者一致，对象ID也必须与作者处于同一个HTTPS origin。

同一个评论对象重复到达时，用主键和 `ON CONFLICT(id) DO NOTHING` 避免重复插入。前面按活动去重，这里按评论对象去重，即使换了一条活动送来同一个评论，也不用在数据库里多占一个位置。

编辑则更麻烦一些。假如读者先发来一句骂我的话，想了想又把它改得温和一点，而网络恰好把旧版本送得更晚，我就会在数据库里替读者恢复其战斗性。为了避免这种多余的激化矛盾，Update除了要匹配原作者，还需要有比现存记录更新的时间；没有可用版本时间的编辑，只好不予应用。

如果读者最后决定把评论删了，我还不能直接把那一行从数据库里删除：删得太干净，数据库就会忘记它曾经被删除过，迟到的Create又能把它插回来。读者本来已经决定不骂了，我这边却替其恢复原状，还显得对方反复无常，实在有些缺德。

因此，删除时只清空内容和作者显示名，记下删除时间，保留对象ID和作者ID作为墓碑。这样，已经存储并删除的评论，再收到迟到的Create或者Update时也不会复活。所谓墓碑，在这里倒也确实有阻止死者重返人间的作用（）。

做到这里，评论终于有地方存了。然而读者打开博客，依然看不到联邦回复，因为**这次只做了存储，还没有接进页面**。现有的Sodesu评论界面照常使用，这边也只接收直接回复文章的Note，回复评论的楼中楼暂且不管。从“没有”进步到了“有，但不给看”，总归也算取得了一些阶段性成果。

而且远端发来的HTML目前只是作为不可信内容保存，以后要展示还得先清洗。总不能前面辛辛苦苦验签、检查作者、比较时间，最后却拿一个 `innerHTML`，把别人的恶意代码美美地送进读者的浏览器。

## 发文章，附赠全集

旧的 `/api/sendToInbox` 会读取全部关注者和outbox，去重收件箱地址，然后做两层循环。下面是简化后的逻辑：

```typescript
for (const inbox of inboxes) {
  for (const item of [...outbox.orderedItems].reverse()) {
    const request = new AppRequest(inbox, {
      body: JSON.stringify(item),
    });
    await request.digestAndSign(env);
    const response = await fetch(request);
    if (!response.ok) {
      return new Response('Delivery failed', { status: 502 });
    }
  }
}
```

容易看出，它对“哪些文章已经发过”和“这次发到了哪里”都毫无记忆。前几个收件箱收完了全部文章，后面某个收件箱返回错误，整个请求就跟着返回502。于是我重新调用接口，前几个收件箱又得从头收一遍——没有共患难，至少可以共收件。

当然，按照ActivityPub的要求，远端应该要根据对象ID去重，但不知为什么订阅者好像就是会收到多份。然而我这边签名和发送的工作是实打实的，所有远端的响应时间还串在同一个请求里。一篇文章写出来以后，竟然需要如此兴师动众地向关注者介绍我的全部创作生涯，也不知道是对自己的文笔有多大信心。

现在改成每五分钟由cron扫描一次文章，把已经到发布日期、但数据库里没见过的slug记成待发布任务。第一次扫描则特殊处理：把当时已经发布的文章标成baseline，建立历史基线，避免刚迁移就向所有关注者重播整个博客。

不过，这个“第一次”也得安排好：部署后先确认基线已经初始化，再部署第一篇希望自动广播的新文章。否则新文章恰好赶上第一次扫描，就会和旧文章一起被登记为历史，尚未出场便已谢幕。日期设在未来的文章则会在到达发布日期后被扫描发现，不用提前给读者报喜。

每次扫描最多放入五篇待发布文章，每个发布任务最多处理25个不同的收件箱。处理完一页，把游标记进D1，再排下一页。

游标需要等这一页的投递消息都成功进入Cloudflare Queues以后才能往前走，否则进度条倒是很好看，消息却不知所终。如果下一页的续接任务没能入队，后面的cron还会从pending记录里把它捞出来继续处理。这样以后，Worker可以中途出些意外，倒也不用每次都从我的第一篇文章开始缅怀。

HTTP请求继续由Astro处理，定时扫描和队列消费则放进Worker入口。Fedify的dispatcher和listener用同一个builder注册，处理具体请求或队列任务时，再绑定当次的D1和Queue。这样，收件箱处理与出站投递都能通过Cloudflare Queues执行，不必把后续工作全塞在一次HTTP请求里。

旧的手动接口也保留了，但现在调用它只是立即触发同一套增量扫描，返回HTTP 202和 `{ "queued": N }`。这个N表示入队的文章发布任务数，最多五个，不是“已经送达多少个关注者”。

## 最后，让它等会儿再试

现在终于不用在一个HTTP请求里等所有人回话了。然而把消息排进队列，并不能顺便把远端服务器修好，对方该掉线还是会掉线，只好等会儿再试。

现在需要重试的失败任务会请求指数退避，延迟从30秒增加到最多一小时；Cloudflare队列配置了12次重试，耗尽后进入死信队列，留待排查和重放。Fedify会区分部分永久HTTP失败，因此也不是每个非成功响应都值得无休止地重发。

文章发布表里的complete也需要稍微解释一下：它表示所有收件箱分页都已经完成入队，**不表示所有远端都已确认收到**。后面的HTTP投递还会独立执行和重试。倘若只看一个“完成”，就宣布所有关注者都已收到新文章，那倒是很有报表治国的风范；真要知道发得怎么样，仍然得去看队列、死信和日志。

而且，“消息入队”和“游标写入D1”并不在同一个跨服务事务里。前者成功、后者还没执行时Worker挂了，下次就可能重发这一页。所以这里仍然可能重复投递，只是保留稳定的Create ID，让远端能认出这是同一条活动。队列能替我存消息，却不能替我让两个服务的写入凭空变成一个原子操作。

当前的发布游标还依赖单消费者推进，因此队列的 `max_concurrency` 配成了1。几个消费者同时来改这一个进度，显然不在当前实现的考虑范围内，先保持一个即可。我写文章的频率倒也没有高到需要为此大搞生产竞赛。

至于给旧文章改几个字，或者删掉文章以后通知远端，目前也还没有做。自动发布认的是新slug，不会为本地文章的编辑和删除生成出站Update、Delete，也不给新关注者补发历史文章。前面接上的评论编辑、删除，是处理别人发来的回复；轮到我自己改文章，待遇反而还差些，留待以后再说。

## 后记

这两次提交还加入和扩充了Worker回归测试，覆盖验签、关注与取消关注、评论的重复投递和越权修改、版本顺序、删除墓碑、历史基线、分页发布、重试以及原有页面和RSS等路径。

测试使用构建后的Astro Worker，在Miniflare里跑D1和队列生产者，再用模拟远端HTTP服务配合驱动消费者。它能检验这些分支是否按预期工作，但不等于已经和每一种真实联邦软件完成了互通测试。部署以后，真实账号的关注、回复、编辑和删除仍然要验证。

折腾完以后，博客页面几乎没有变化，读者依然是在原来的地方看原来的文章，联邦评论甚至还没显示出来。如果只看页面截图，这次改造大概可以算什么都没干。然而打开代码，至少收到的评论不再直接扔掉，发到一半的文章不再从头再来，验签文件也终于不只是待在仓库里充门面了。

写这些代码时，我也觉得一个个人博客竟然有这么多事情要管，实在折腾。不过等这些事情不再出错，我大概又会忘掉它们，去找些新的功能给自己添麻烦。眼下还有现成的：先把已经存下来的评论显示出来，免得读者以为我又把其发言扔了——这回真没扔，只是还没拿出来。
